Gatherersで、中間操作を自作する。

Stream APIのmap・filter・collectとラムダ式を使える方向け。組み込みGathererの使い方から、状態・打ち切り・finisher・並列対応を持つ自作Gatherer、合成の実習まで10問で練習します。まず出力を予想し、各問題の回答を開いて確かめましょう。

  • downstream（下流）：Gathererの次に続く段階。downstream.push(e)で要素を渡します。戻り値は「下流がまだ要素を受け付けるか」です。

01 / 基本と組み込みGatherer

問題 01 · 4つの構成要素・Collectorとの違い

Gathererは、何を組み合わせてできている？

Gathererは次の4つの関数で構成されます。それぞれ「いつ呼ばれ、何をするか」を答えてください。

initializer   Supplier<A>
integrator    Gatherer.Integrator<A, T, R>
combiner      BinaryOperator<A>
finisher      BiConsumer<A, Gatherer.Downstream<? super R>>

あわせて、Gatherer<T, A, R>の型引数T・A・Rの意味と、Collector（collectに渡すもの）との違いを1文で説明してください。

回答・解説を開く
  • initializer：処理の開始時に1回呼ばれ、状態オブジェクトを作ります。状態が不要なら省略します。
  • integrator：入力要素ごとに呼ばれ、状態を更新し、必要に応じて下流へpushします。falseを返すと処理を打ち切ります。
  • combiner：並列実行時に、分割して処理した2つの状態をまとめます。
  • finisher：入力がすべて尽きた後に1回呼ばれ、状態に残った要素を下流へpushできます。

Tは入力要素の型、Aは状態（state）の型、Rは下流へ流す出力要素の型です。

Collectorは終端操作として1つの結果を返しますが、Gathererは中間操作として任意個の要素をStreamに流し、後ろにさらにmapなどを続けられます。

省略した要素にはGatherer.defaultInitializer()などの既定値が使われます。4つすべてを毎回書く必要はありません。

窓の中身の集計は、gatherの後に続く通常のmapで行えます。

問題 03 · fold / scan

最終結果だけか、途中経過も全部か

初期残高1000の口座に、入出金List.of(500, -300, 100, -700)が順に発生しました。

  1. 各取引後の残高推移[1500, 1200, 1300, 600]を得るコードを書いてください。
  2. 最終残高だけを得るコードを書き、その戻り値がどんなStreamになるか答えてください。
  3. 2のコードに空のリストを渡すと、結果はどうなりますか？

コードで解く：src/main/java/gatherers/Q03FoldScan.javaのTODOを実装し、./gradlew test --tests '*Q03*'ですべてのテストが通ることを確認します。

回答・解説を開く
// 1. 途中経過をすべて流す
transactions.stream()
    .gather(Gatherers.scan(() -> 1000, Integer::sum))
    .toList();          // => [1500, 1200, 1300, 600]

// 2. 最終結果だけを流す
transactions.stream()
    .gather(Gatherers.fold(() -> 1000, Integer::sum))
    .toList();          // => [600]

scanは1要素ごとに更新した値を流し、foldは入力が尽きたときに最終値を1つだけ流します。foldの結果も中間操作の出力なので、要素1つのStreamです。値を取り出すにはfindFirst()などの終端操作を続けます。

3の答えは[1000]です。foldは入力が空でも初期値を1つ流します。一方、scanは入力が空なら何も流しません。

reduceと異なり、foldは結合法則を満たす関数や並列用のマージ関数を必要としない、順序どおりの集約です。

02 / Gathererを自作する

問題 04 · Gatherer.of・Integrator.ofGreedy

mapをGathererで作り直す

次のシグネチャで、Stream.mapと同じ働きをするGathererを実装してください。状態は不要です。

static <T, R> Gatherer<T, ?, R> map(Function<? super T, ? extends R> mapper)

Stream.of(1, 2, 3).gather(map(x -> x * 2)).toList();   // => [2, 4, 6]

integratorが返すbooleanには何を返すべきですか？ 常にtrueを返す実装との違いも説明してください。

コードで解く：src/main/java/gatherers/Q04Map.javaのTODOを実装し、./gradlew test --tests '*Q04*'ですべてのテストが通ることを確認します。

回答・解説を開く
static <T, R> Gatherer<T, ?, R> map(Function<? super T, ? extends R> mapper) {
    return Gatherer.of(Gatherer.Integrator.ofGreedy(
            (_, element, downstream) -> downstream.push(mapper.apply(element))));
}

状態を使わないのでGatherer.of(integrator)だけで作れます。integratorの第1引数（状態）は使わないため_にします。

downstream.pushの戻り値をそのまま返します。後ろにlimit(1)などがあると下流は要素を受け付けなくなり、pushはfalseを返します。それを上流へ伝えることで、無駄な処理を止められます。常にtrueを返すと、下流が不要になった後も入力を読み続けます。

このGathererは自分からは打ち切らないので、Integrator.ofGreedyで包んで「貪欲である」とStreamに伝えます。結果は変わりませんが、実行時の最適化に使われます。

問題 05 · 短絡・無限ストリーム

条件を外れた要素まで含めて止める

takeWhileは条件を満たさない最初の要素を含めません。その要素も含めて止まるtakeWhileInclusiveを実装してください。

static <T> Gatherer<T, ?, T> takeWhileInclusive(Predicate<? super T> predicate)

Stream.of(3, 5, 4, 2, 1).gather(takeWhileInclusive(x -> x != 4)).toList();
    // => [3, 5, 4]
Stream.iterate(1, i -> i + 1).gather(takeWhileInclusive(x -> x < 5)).toList();
    // => [1, 2, 3, 4, 5]（無限ストリームでも止まる）

このintegratorをIntegrator.ofGreedyで包んでよいかも答えてください。

コードで解く：src/main/java/gatherers/Q05TakeWhileInclusive.javaのTODOを実装し、./gradlew test --tests '*Q05*'ですべてのテストが通ることを確認します。

回答・解説を開く
static <T> Gatherer<T, ?, T> takeWhileInclusive(Predicate<? super T> predicate) {
    return Gatherer.of((_, element, downstream) ->
            downstream.push(element) && predicate.test(element));
}

先に要素をpushしてから条件を判定し、条件を外れたらfalseを返します。integratorがfalseを返すと上流からの入力が止まるため、Stream.iterateの無限ストリームでも終了します。

&&の左側をpushにしているので、下流が受け付けなくなった場合もfalseを返して止まります。

ofGreedyで包んではいけません。このGathererは自分から打ち切るため、greedyではありません。Gatherer.ofに渡すラムダは、通常のIntegratorとして扱われます。

問題 06 · ofSequential・状態

キーで重複を判定して、最初の要素だけ残す

distinctは要素そのもののequalsで重複を判定します。キー抽出関数で判定するdistinctByを実装してください。

static <T, K> Gatherer<T, ?, T> distinctBy(Function<? super T, ? extends K> keyExtractor)

Stream.of("apple", "avocado", "banana", "blueberry", "cherry")
    .gather(distinctBy(s -> s.charAt(0)))
    .toList();          // => [apple, banana, cherry]

状態にはどんな型を使い、どのファクトリメソッドで作りますか？ 状態をrecordにしてはいけない理由も答えてください。

コードで解く：src/main/java/gatherers/Q06DistinctBy.javaのTODOを実装し、./gradlew test --tests '*Q06*'ですべてのテストが通ることを確認します。

回答・解説を開く
static <T, K> Gatherer<T, ?, T> distinctBy(Function<? super T, ? extends K> keyExtractor) {
    return Gatherer.ofSequential(
            HashSet<K>::new,
            Gatherer.Integrator.ofGreedy((seen, element, downstream) -> {
                if (seen.add(keyExtractor.apply(element))) {
                    return downstream.push(element);
                }
                return true;
            }));
}

出現済みのキーをHashSetで記録します。Set.addは初めて追加したときだけtrueを返すので、その要素だけを流します。重複した要素は流さず、処理は続けるためtrueを返します。

「最初に現れた要素」は入力順に依存するため、ofSequential(initializer, integrator)で逐次処理のGathererにします。initializerは評価ごとに呼ばれるので、同じGathererを複数のStreamで使っても状態は共有されません。

integratorは状態の参照を受け取り、中身を書き換えます。recordのフィールドは再代入できないため、状態はHashSetや可変のクラスにします。

問題 07 · finisher・最後の要素の取りこぼし

最後のまとまりが消えるバグを直す

連続する同じ文字列を「文字列＋連続数」にまとめる（ランレングス圧縮）Gathererを書いたところ、最後のまとまりが出力されませんでした。原因と修正方法を答えてください。また、integratorだけでは直せずfinisherが必要になる理由も説明してください。

class RunState { String value; int count; }

Gatherer<String, RunState, String> runLength = Gatherer.ofSequential(
        RunState::new,
        (state, element, downstream) -> {
            if (state.count > 0 && state.value.equals(element)) {
                state.count++;
                return true;
            }
            boolean accepted = state.count == 0
                    || downstream.push(state.value + state.count);
            state.value = element;
            state.count = 1;
            return accepted;
        });

Stream.of("a", "a", "a", "b", "c", "c").gather(runLength).toList();
    // 期待：[a3, b1, c2]　実際：[a3, b1]

コードで解く：src/main/java/gatherers/Q07RunLength.javaに問題文のコードが入っています。これを修正し、./gradlew test --tests '*Q07*'ですべてのテストが通ることを確認します。

回答・解説を開く

integratorは「届いた要素が、数えている最中の文字（state.value）と違うとき」に前のまとまりを流します。stateは最初に1つ作られたRunStateがずっと使い回され、フィールドが書き換わるだけです。最後のc2の後には次の要素が来ないため、integratorでは流すきっかけがありません。入力が尽きた後に呼ばれるfinisherで、状態に残ったまとまりを流します。

Gatherer<String, RunState, String> runLength = Gatherer.ofSequential(
        RunState::new,
        (state, element, downstream) -> { /* 問題文と同じ */ },
        (state, downstream) -> {
            if (state.count > 0) {
                downstream.push(state.value + state.count);
            }
        });
    // => [a3, b1, c2]

finisherが必要になる理由：integratorのif文は2つの分岐に分かれ、pushは片方でしか起きません。

  • ① 届いた文字が数えている文字と同じ：countを1増やすだけで、pushしません。
  • ② 届いた文字が違う（または最初の1個目）：それまでのまとまりをpushし、新しい文字を数え始めます。

入力a a a b c cで、どちらの分岐を通るかを追います。

届いた要素呼ばれる前のstate通る分岐push
a(なし, 0)②（最初の1個目）なし（count==0なので）
a(a, 1)① 同じなし
a(a, 2)① 同じなし
b(a, 3)② 違う"a3"
c(b, 1)② 違う"b1"
c(c, 1)① 同じなし
（終わり）(c, 2)integratorは呼ばれないなし ← ここが問題

"c2"をpushするには②を通る必要があり、そのためには「cとは違う文字」が届かなければなりません。しかし入力はもう終わっていて、integratorは要素が届かないと呼ばれないため、(c, 2)はstateに残ったままになります。

このGathererは、あるまとまりを「次の違う文字が来たとき」に初めて流します。届いた時点では、その連続がまだ続くのか分からないからです。たとえば5回目の"c"の時点で"c1"を流すと、次にもう1つ"c"が来て間違いになります。

最後のまとまりc × 2には「次の違う文字」が永遠に来ません。integratorは要素が届いたときにしか呼ばれないので、要素が来なければ流す機会もありません。そこで「入力はもう終わった」というタイミングで1回だけ呼ばれるfinisherが必要になります。finisherの中なら「もう続きは来ない」と確定しているので、状態に残ったc × 2を安心して流せます。

state.count > 0の確認により、空のStreamでは何も流しません。この確認がないとnull0のような値を流してしまいます。

窓分割やfoldのように「ためてから流す」Gathererには、finisherが必要になることが多いです。windowFixedが端数の窓を最後に流せるのも同じ仕組みです。

問題 09 · combiner・並列実行

parallel()でも正しい上位n件

Integerの上位n件を降順で流すtopNを、parallel()でも正しく動くように実装してください。

    // => [1000, 999, 998]
IntStream.rangeClosed(1, 1000).boxed().parallel().gather(topN(3)).toList();
    // => [1000, 999, 998]

どのファクトリメソッドを使い、combinerで何をしますか？ ofSequentialで作ったGathererをparallel()のStreamで使うとどうなるかも答えてください。

コードで解く：src/main/java/gatherers/Q09TopN.javaのTODOを実装し、./gradlew test --tests '*Q09*'ですべてのテストが通ることを確認します。

回答・解説を開く
static Gatherer<Integer, ?, Integer> topN(int n) {
    return Gatherer.<Integer, PriorityQueue<Integer>, Integer>of(
            PriorityQueue::new,
            Gatherer.Integrator.ofGreedy((heap, element, _) -> {
                heap.offer(element);
                if (heap.size() > n) {
                    heap.poll();          // 最小を捨てて n 件に保つ
                }
                return true;
            }),
            (left, right) -> {
                for (Integer e : right) {
                    left.offer(e);
                    if (left.size() > n) {
                        left.poll();
                    }
                }
                return left;
            },
            (heap, downstream) -> {
                List<Integer> sorted = new ArrayList<>(heap);
                sorted.sort(Comparator.reverseOrder());
                for (Integer e : sorted) {
                    if (!downstream.push(e)) {
                        return;
                    }
                }
            });
}

4つすべてを受け取るGatherer.of(initializer, integrator, combiner, finisher)を使います。並列実行では入力が分割され、分割ごとにinitializerで状態が作られます。combinerは2つの部分結果をマージし、再びn件に絞ります。integratorでは要素を流さないので、下流の引数は_にします。

PriorityQueueとは：java.util.PriorityQueueは、入れた順ではなく優先度の順に取り出せるキューです。内部はヒープという木構造で、Comparatorを指定しなければ要素の自然順序で「最小の要素」が常に先頭に来ます（最小ヒープ）。主な操作は次のとおりです。

  • offer(e)：要素を追加します。O(log n)。
  • peek()：先頭（最小）を取り出さずに見ます。O(1)。
  • poll()：先頭（最小）を取り出して削除します。O(log n)。
  • size()：要素数を返します。

ヒープが保証するのは「先頭が最小」ということだけで、それ以外の要素の並びは整列されていません。そのためfor文やnew ArrayList<>(heap)で取り出した順序はバラバラです。降順に流すには、finisherで並べ替えます。

上位n件なのに最小ヒープを使う理由：上位n件を残すには、n件を超えたときに「残っている中で一番小さいもの」を捨てる必要があります。最小ヒープなら捨てる対象が常に先頭にあるので、poll()ですぐ捨てられます。状態はn件（一時的にn+1件）しか持たないため、全要素をためてソートするよりメモリを使いません。

5[5]いいえ[5]
1[1, 5]いいえ[1, 5]
8[1, 5, 8]いいえ[1, 5, 8]
3[1, 3, 5, 8]はい → 最小の1を捨てる[3, 5, 8]
9[3, 5, 8, 9]はい → 最小の3を捨てる[5, 8, 9]
（終わり）finisherで降順に並べて 9, 8, 5 を流す

combinerでも同じ考え方で、rightの要素をleftに1つずつofferし、n件を超えたらpollで最小を捨てます。

ofSequentialで作ったGathererなどcombinerを持たないものは、parallel()のStreamでもgatherの段階が逐次に評価されます。結果は正しいままですが、並列化の効果は得られません。

public static Gatherer<Integer, ?, Integer> pipeline() {
    return Gatherers.<Integer>windowFixed(2)
            .andThen(Q04Map.map(window -> window.stream().mapToInt(Integer::intValue).sum()))
            .andThen(Gatherers.scan(() -> 0, Integer::sum));
}
// main の出力
[3, 10, 21, 36, 55]
[3, 6]

1行目は、窓[1, 2] … [9, 10]の合計3, 7, 11, 15, 19の累積和です。2行目は窓[1, 2]と端数の[3]の合計3, 3の累積和になります。

a.andThen(b)は「aの出力をbの入力にする」Gathererを作ります。.gather(a).gather(b)と同じ結果ですが、合成したGathererを名前付きの部品として再利用できます。windowFixedには型引数<Integer>を明示し、後続のラムダの型推論を助けています。

Q10PipelineはQ04Map.mapを使うため、問題04を先に解いておく必要があります。mainは Java 25 で正式化された引数なしの形です。
